# ADBPG Hybrid Search Benchmark

BioASQ 1024-d cosine datasets for two complementary benchmark families:

- `HybridUnifiedPerformanceCase`: scalar, array, and JSON predicates derived
  from the same percentile truth set and sharing one GT file per selectivity.
- `HybridJoinPerformanceCase`: a separate realistic 1:N chunk-to-document
  model whose clustered hits require its own GT.

This is the canonical guide for the ADBPG hybrid benchmark client, dataset
generation, master-only loading, and result interpretation. Generated
datasets, logs, and run results are local artifacts and are not part of this
branch.

## Layout

```
datasets/
├── bioasq_hybrid_medium_1m/   # base = 1,000,000 vectors
│   ├── test.parquet                          # fixed 500 query vectors
│   ├── query_ids.json                        # stable hybrid-query-v1 order
│   ├── neighbors.parquet                     # pure ANN top-1000 GT
│   ├── neighbors_hybrid_<rate>.parquet        # generated unified GT
│   └── neighbors_join_{50p,10p,1p,0.10p,0.01p}.parquet
└── bioasq_hybrid_large_10m/   # base = 10,000,000 vectors
    ├── test.parquet                          # fixed 500 query vectors
    ├── query_ids.json
    ├── neighbors_hybrid_<rate>.parquet        # generated unified GT
    └── neighbors_join_{50p,10p,1p,0.10p,0.01p}.parquet
```

`<rate>` is the post-filter selectivity. The unified default grid is
0.1%, 1%, 5%, 10%, 20%, 22%, 25%, 30%, 40%, 50%, 55%, 60%, 70%, 80%,
and 90%. Scalar, array, and JSON predicates at a given rate all reference
the same `neighbors_hybrid_<rate>.parquet`.

The scalar `percentile` value is a deterministic hash bucket in `[0, 100000)`.
For example, 0.1% uses `percentile < 100` and 1% uses
`percentile < 1000`; array and JSON markers express the same nested truth sets.

All three unified predicates select exactly the same rows:

| Filter type | Generated column | Predicate |
|---|---|---|
| Scalar | `percentile INTEGER` | `percentile < rate * 100000` |
| Array | `user_array TEXT[]` | `user_array @> ARRAY['r_<bp>bp']` |
| JSON | `payload JSONB` | `payload @> '{"rates":["r_<bp>bp"]}'` |

`user_array` contains 45 deterministic filler tokens plus the nested rate
markers that match the row. `payload.rates` contains the same markers. A
single `neighbors_hybrid_<rate>.parquet` is therefore a fair GT for all three
SQL representations.

The formal dataset uses a stable hash-selected set of 500 queries and Top1000
GT. A quick dataset generated with `--test-size N` is always a prefix of this
same query order.

The retained Join fixtures use the legacy reciprocal grid:

| Suffix | Selectivity | `--hybrid-rate` |
|---|---|---|
| `50p`   | 50%   | 0.5    |
| `10p`   | 10%   | 0.1    |
| `1p`    | 1%    | 0.01   |
| `0.10p` | 0.1%  | 0.001  |
| `0.01p` | 0.01% | 0.0001 |

The Join files target `HybridJoinPerformanceCase` (vector ⋈ side-table
`array_overlap`). The retired standalone `HybridArrayPerformanceCase` is
available on the original `hybrid_bench` branch for historical reports.

## Train shards: download from VectorDBBench's Aliyun OSS

The base vectors (`shuffle_train*.parquet`) are NOT tracked in git — together they are ~40 GB.
They come from the same BioASQ corpus that upstream VectorDBBench publishes on the public
Aliyun OSS bucket (anonymous read, no key required):

```
oss://assets.zilliz.com.cn/benchmark/bioasq_medium_1m/shuffle_train.parquet
oss://assets.zilliz.com.cn/benchmark/bioasq_large_10m/shuffle_train-{00..09}-of-10.parquet
```

This is the same endpoint `AliyunOSSReader` already uses (see
`vectordb_bench/__init__.py` → `ALIYUN_OSS_URL = "assets.zilliz.com.cn/benchmark/"`
and `vectordb_bench/backend/data_source.py::AliyunOSSReader`).

### Option A — let VectorDBBench fetch on first run (recommended)

Switch the dataset source to AliyunOSS and point `DATASET_LOCAL_DIR` at this folder; the CLI
(or the web UI's "Dataset from Aliyun (Shanghai)" checkbox) will download missing train
shards into `bioasq_hybrid_medium_1m/` (or `bioasq_hybrid_large_10m/`) on first run.

```bash
export VECTORDB_BENCH_DATASET_SOURCE=AliyunOSS
export DATASET_LOCAL_DIR=<repo>/datasets
```

### Option B — pre-download with ossutil

```bash
# 1M
mkdir -p <repo>/datasets/bioasq_hybrid_medium_1m
ossutil cp -r oss://assets.zilliz.com.cn/benchmark/bioasq_medium_1m/ \
  <repo>/datasets/bioasq_hybrid_medium_1m/ --include "shuffle_train*.parquet"

# 10M
mkdir -p <repo>/datasets/bioasq_hybrid_large_10m
ossutil cp -r oss://assets.zilliz.com.cn/benchmark/bioasq_large_10m/ \
  <repo>/datasets/bioasq_hybrid_large_10m/ --include "shuffle_train*.parquet"
```

> Note: upstream stores the train shards under `bioasq_medium_1m/` / `bioasq_large_10m/`
> (no `_hybrid_` suffix). The `_hybrid_` directories in this repo are the bench's custom
> case dirs. Download or symlink the train shards into them. Unified
> `test.parquet`, `query_ids.json`, `metadata.json`, and
> `neighbors_hybrid_*.parquet` are generated by the script below.

## Usage with VectorDBBench

```bash
export DATASET_LOCAL_DIR=$(pwd)/datasets   # parent dir of the two case dirs

vectordbbench adbpgnova ... \
  --custom-dataset-name bioasq_hybrid_medium_1m \
  --custom-dataset-dir . \
  --custom-dataset-with-gt \
  --case-type HybridUnifiedPerformanceCase \
  --hybrid-mode unified \
  --hybrid-filter-type array \
  --hybrid-rate 0.2
```

Generate the 1M unified dataset:

```bash
python scripts/construct_hybrid_dataset.py \
  --src /data/bioasq/bioasq_medium_1m \
  --dst datasets/bioasq_hybrid_medium_1m \
  --train-file shuffle_train.parquet \
  --rates 0.001 0.01 \
  --modes unified \
  --topk 1000
```

Generate the formal 10M dataset while keeping the existing train shards:

```bash
python scripts/construct_hybrid_dataset.py \
  --src /data/bioasq/bioasq_large_10m \
  --dst /data/bioasq/bioasq_large_10m_hybrid_500q_top1000 \
  --train-glob 'shuffle_train-*-of-10.parquet' \
  --rates 0.001 0.01 --modes unified --topk 1000 \
  --skip-train-write --skip-full-gt
```

For the 10M layout, symlink the source train shards into `--dst` so the
query client and master-only preparation script use one self-contained
dataset directory. `metadata.json` records the generated dataset contract.

The full run always uses the stable 500-query set and writes top-1000 GT.
For a quick development check, `--test-size N` uses the first `N` queries
from that same fixed order; for example, `--test-size 5 --topk 10`.

Use `--train-size`, `--test-size`, and a smaller `--topk` for a smoke test.

Use `--modes join` only for the independent multi-table benchmark.

## Master-only preparation

For a coordinator-local baseline, prepare the table outside VectorDBBench. The
preparation script creates a real ADBPG entry table, runs one independent COPY
connection per train shard, builds B-tree/GIN indexes after loading, and then
builds NovaMR with its internal parallel workers:

```bash
python scripts/prepare_hybrid_master_only.py \
  --dataset-dir /data/bioasq/bioasq_large_10m_hybrid_500q_top1000 \
  --table vector \
  --host <host> --port <port> --db-name postgres --user <user> \
  --workers 10 --expected-rows 10000000 --drop-existing \
  --algorithm novamr --rabitq-bits 7 \
  --hnsw-m 48 --ef-construction 600 \
  --build-parallel-processes 32
```

The script verifies both invariants before returning:

- no row exists in `gp_distribution_policy` for the table;
- sampled data reports `gp_segment_id = -1`.

Run VectorDBBench in query-only mode against the prepared table:

```bash
DATASET_LOCAL_DIR=/data PYTHONPATH=. \
python3 -m vectordb_bench.cli.vectordbbench adbpgnova \
  --skip-drop-old --skip-load --search-serial --skip-search-concurrent \
  --case-type HybridUnifiedPerformanceCase \
  --custom-case-name bioasq10m_hybrid_500q \
  --custom-dataset-name bioasq \
  --custom-dataset-dir bioasq_large_10m_hybrid_500q_top1000 \
  --custom-dataset-size 10000000 --custom-dataset-dim 1024 \
  --custom-dataset-file-count 10 --custom-dataset-use-shuffled \
  --custom-dataset-with-gt \
  --hybrid-mode unified --hybrid-storage master_only \
  --hybrid-filter-type array --hybrid-rate 0.001 \
  --user-name <user> --password '<password>' \
  --host <host> --port <port> --db-name postgres \
  --algorithm novamr --k 100 --serial-query-count 500 --force-plan auto
```

`--hybrid-storage master_only` rejects distributed tables and also rejects the
built-in load stage. This prevents a benchmark run from silently falling back
to the single-connection loader or from measuring a 3-segment MPP table.

## Plan control and metrics

`--force-plan` makes plan comparisons independent of selectivity-estimation
errors:

| Value | Purpose |
|---|---|
| `auto` | Validate the out-of-box planner decision |
| `brute_force` | Force B-tree/GIN + exact sort |
| `bitmap_pushdown` | Force ANN with bitmap pushdown |
| `post_filter` | Force ANN post-filter |
| `expression` | Force expression pushdown |

Use `--explain-only` for a fast plan check. Use `--serial-query-count 5` or
`20` for a client smoke test and `500` for formal measurements.

Serial output includes per-query `SERIAL_QUERY_RESULT` records and aggregate
Recall@K, NDCG, average/P95/P99 latency, minimum returned row count, and the
number/rate of queries returning fewer than TopK rows.
